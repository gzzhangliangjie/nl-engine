00 · Overview

用底层图形 API 手撸一套「Nanite + Lumen」

这不是 Epic 的源码笔记，而是一条自研路线的地图：几何怎么虚拟化、光照怎么动态化、以及两者之间那道最容易被忽略的接缝。

先建立三层心智模型

GEOMETRY

几何层 · Nanite

把网格切成 128 三角的 cluster，逐层简化成 DAG，运行时按屏幕误差选一条「cut」，只画真正需要的簇。

产出物：可见性缓冲、每像素 cluster/triangle id。

LIGHTING

光照层 · Lumen

屏幕探针收集入射辐射度，命中点去世界缓存查辐照度，多帧累积收敛，最后逐像素插值 + 降噪。

产出物：间接漫反射、间接高光。

GLUE

接缝层 · BVH

虚拟几何没有「LOD n」这种全局索引，光追要求三角稳定存在。这道接缝决定了你整套系统的内存与帧时间上限。

常见解：fallback mesh / 逐簇 BLAS 聚合 / 自建 BVH。

一句话结论：Nanite 和 Lumen 单独做都有人跑通过，真正难的是中间那一层——光追加速结构怎么从「会随视角变化的簇集合」里长出来。所以本库把 03 章单独拎出来讲。

整体数据流

01 · Virtualized Geometry

Nanite：把「LOD」从美术的手工活变成运行时的算法

核心只有一句话：把模型切成一堆小簇，逐级简化成一张有向无环图，运行时按屏幕误差挑出一组恰好够用的簇来画。

1.1 为什么传统 LOD 不够用

传统做法是「一个模型几个 LOD」，选择粒度是整个模型。问题在于：一栋建筑离你 5 米，你只能在地面细节和整栋楼之间二选一——要么浪费几十万面去画看不见的屋顶，要么整栋楼糊成一片。虚拟几何把粒度降到 128 个三角形，于是同一个模型的不同部位可以处在不同细节级别。

关键概念「cut」：在 DAG 上选一组节点，使得从根往下走，每个分支恰好在一个节点处被切断。这组节点就是本帧要画的簇。相邻簇共享边界顶点，所以不会出现裂缝。

1.2 三个数字先记住

参数典型值为什么是这个值
簇大小128 三角 / 128 顶点小到剔除粒度足够细，大到顶点数据能塞进 L1、单个 workgroup 能处理完。索引可用 u8 打包，省 4 倍带宽。
分组大小32 簇一组简化必须成组做，否则簇边界被反复锁定，简化质量崩掉。组内简化后再重新切簇。
LOD 误差阈值1 像素「这个簇简化带来的几何误差投影到屏幕上小于 1 像素」就允许用它，肉眼看不出。

1.3 离线管线的五个步骤

  1. 切簇（clusterize）

    用 meshoptimizer 的 meshopt_buildMeshlets：按连通性贪心生长，控制每簇三角/顶点上限，输出每簇的索引与顶点索引表。注意它同时给出包围球和法线锥，后面剔除要用。

  2. 聚组（partition）

    把相邻簇聚成约 32 簇一组。原版 UE 用 METIS 做图划分（考虑簇间邻接权重），meshoptimizer 现在也有自己的 partitioner，可以省掉 METIS 这个重依赖。

  3. 组内简化（simplify）

    把一组簇当成一个整体做 QEM 边折叠简化到目标误差，但要把组边界顶点锁住（locked vertices）——否则父层和子层的接缝会裂开。锁边界的代价是简化率下降，这也是为什么要「成组简化再重切」而不是逐簇简化。

  4. 重切 + 递归

    简化后的组重新切成 128 三角的簇，作为上一层节点；重复直到剩一个簇（根）。父子关系记录下来就是 DAG（严格说是树 + 多条父边）。

  5. 误差与打包

    每层记录「本层简化引入的几何误差」，父层误差 = 子层误差 + 本次简化误差（单调不减，这是无缝切换的前提）。顶点位置量化到 16 位、法线八面体编码到 2×8 位、UV 量化，连同包围球/锥、误差、子节点偏移一起写进二进制。

1.4 运行时：一条 GPU 驱动的流水线

Pass做什么要点
实例剔除对所有实例做视锥/距离/背面锥剔除用 IndirectDispatch 的计数做压缩，下游只处理存活实例
DAG 遍历从根往下走，算每层簇的屏幕误差「persistent threads」模型：一个线程负责一个簇，递归时自己去抢队列；也可用节点栈式遍历
遮挡剔除用上一帧 Hi-Z 金字塔判断簇包围球是否被挡两遍：第一遍只画大簇当遮挡体，第二遍再放开小簇，避免大量误判
光栅化大三角走硬件，小三角走 compute 软光栅阈值通常 1~2 像素边长的三角，具体看 GPU 的 quad 利用率
材质解析从 vis buffer 反解几何属性，算材质、写 GBuffer先做深度预通道（只算位移/遮罩），再只对最终可见像素跑完整材质
可见性缓冲为什么这么设计：一个 64 位整数里，高 32 位放深度（浮点位模式），低 32 位放 instanceId << 8 | triangleId。用 atomicMax 一次操作同时完成深度测试和像素归属写入，不需要深度附件、不需要锁。UE 的原始做法就是这么省下带宽的。

软光栅化的三个硬性要求

  • 64 位原子操作：Vulkan 要 VK_KHR_shader_atomic_int64 / shaderBufferInt64Atomics；WebGPU 没有，所以 nanite-webgpu 只能把深度压成 u16 + 法线 2×u8 塞进 32 位，精度惨烈——这也是它自陈的最大妥协。
  • 以 2×2 像素 quad 为单位走扫描线，保证同一 warp 内的像素对齐，否则吞吐掉一半。
  • 溢出队列：边长超过阈值的大三角会瞬间把工作队列撑爆，要按「每线程固定预算 + 溢出链表」处理，不能无界循环。

02 · Dynamic Global Illumination

Lumen：把「一盏灯照亮整间屋子」变成每帧能算完的事

它不是一个算法，而是一套缓存层级：屏幕探针负责「看得见的地方」，世界缓存负责「看不见的地方」，SDF/光追负责「到底撞到哪」。

2.1 原始问题：为什么 GI 这么贵

渲染方程要求对半球积分，实时里每像素只有 1~2 条射线的预算，而收敛需要成百上千条。所有实时 GI 的本质都是用时间换采样、用缓存换重复计算：这一帧算不完的，靠上一帧的结果补；这一像素算不全的，靠邻居插值补。

2.5 世界缓存：一个 GPU 上的 hashmap

// cell: 世界空间网格，边长 = 探针间距 * 大系数（典型 1~4 米）
struct Cell {
  uvec3  coord;         // 网格坐标，做 hash key
  vec3   irradiance;    // RGB 辐照度（已除 pi 或用 SH）
  float  life;          // 每帧 -1，访问时重置；归零则回收
  uint   hashNext;      // 冲突链（开放寻址也行，但要能回收）
};

// 每帧三件事：
// 1) 对所有存活 cell 衰减 life，compaction 成紧凑数组提高占用率
// 2) 每个 cell 追 1 条向光源的射线（直接光）+ 1 条随机方向射线（查别的 cell，形成多跳）
// 3) 新 cell 插入：先查表，冲突则写链首
为什么不用固定 3D 网格：场景是世界级的，固定网格在垂直方向会浪费 90% 内存。哈希表能只为「真的被射线访问过的地方」分配单元，代价是要处理冲突和回收——这正是 Carrot 那篇 GI 文章里花最多篇幅讲的部分。

2.6 三条可选的技术阶梯

LEVEL 1

DDGI 探针网格

规则的 3D 探针网格 + 八面体深度/辐照度，实现简单、结果稳定，但没有自适应精度，大场景内存爆。

适合：第一版跑通管线，验证你的 GBuffer 和光追是通的。

LEVEL 2

Screen Probe + World Cache

Lumen GI-1.0 的骨架。屏幕探针解决精度分布，世界缓存解决屏外与多跳。

适合：真正的目标方案，投入产出比最高。

LEVEL 3

ReSTIR GI / PT

用 reservoir 重采样把有效采样率拉高一个数量级，配合降噪器可接近路径追踪质量。

适合：最后一步优化，先把 L2 的噪声问题量化清楚再上。

03 · The Seam

接口层：虚拟几何怎么喂给光线追踪

这是整套系统里唯一没有「标准答案」的地方，也是绝大多数自研项目卡死的地方。

3.1 矛盾在哪

光追需要一份稳定、完整、与视角无关的三角形集合来建 BLAS；虚拟几何提供的却是一份每帧变化、只包含可见部分的簇集合。更麻烦的是，模型的不同部位处在不同层级，你无法用「这个模型的 LOD 索引是 2」这种方式描述它。

3.2 三种解法对比

方案做法优点代价
Fallback Mesh
UE 的选择		 离线为每个网格生成一份低模（约 1%~5% 面数）专供光追，与渲染用的簇完全解耦 实现极简，光追场景一次建好不再变；内存可控 光追几何精度低于光栅化，近处反射/阴影会「糊」，需要额外的屏幕空间补偿
逐簇 BLAS 聚合
Carrot 的选择		 资产管线里预建每个簇的 BLAS；每帧从 GPU 回读「本帧需要的簇列表」，把预建 BLAS 拷进当帧的聚合 BLAS，再生成 TLAS 实例 光追精度与光栅化一致，支持流式 回读有 CPU 同步开销；预建 BLAS 常驻显存，内存开销大；BLAS 拷贝本身在部分驱动上不便宜
自建 BVH
Intel 的路子		 不用硬件光追，自己维护一份压缩几何的 BVH，在 compute 里软件遍历 完全掌控精度与内存，不依赖 RT 硬件 遍历性能靠自己优化，工作量最大；等于重写一个光追后端
实测经验：「每帧重建 BLAS」是行不通的——即便在 2024 年的硬件上，对几万个簇重建 BLAS 也要几十毫秒。可用的只有「预建 + 拷贝」或「用低模」。

3.3 逐簇聚合的每帧流程

  1. GPU 侧选出簇列表

    复用 DAG 遍历的结果，把「本帧确定要画 + 可能对光追有贡献」的簇 id 压缩进一个 buffer。注意要包含屏幕外但影响 GI 的簇，不能只取可见簇。

  2. 回读到 CPU（或 GPU 侧间接）

    Vulkan 支持 vkCmdBuildAccelerationStructuresIndirectKHR，可以让 GPU 直接驱动 BLAS 构建，省掉回读。但「从预建 BLAS 拷贝」这一路径目前只能由 CPU 发命令，所以多数项目仍保留一次小规模回读。

  3. 聚合 BLAS

    为本帧的簇集合建一个顶层几何体，用 vkCmdCopyAccelerationStructureKHR 把每个预建 BLAS 拷进对应 offset，这一步是纯显存拷贝，比重建快一个数量级。

  4. TLAS 实例化

    每个网格实例指向它自己的聚合 BLAS；实例 transform 用本帧的世界矩阵。这样实例化开销与网格数成正比，与簇数无关。

  5. 射线查询

    Lumen 侧统一走 rayQueryEXT（compute 里做 GI 更简单，不需要 RT pipeline 的 SBT 那套基础设施）。

3.4 工程上的取舍建议

  • 第一版无脑用 fallback mesh。先把 Lumen 的探针、世界缓存、降噪跑通，视觉上「光追几何略糊」你几乎察觉不到，因为 GI 本身就是低频的。
  • 只对近处做逐簇精度。把场景按距离分层：10 米内用聚合 BLAS 追高精度，之外用 fallback。反射里最容易看出差异的就是近处地面和高光物体。
  • 把「簇列表」和「光栅化列表」分开。前者要包含屏幕外但对 GI 有贡献的簇，后者只要可见簇；混用会漏光。
04 · Reference Code

关键算法伪码

不追求可直接编译，追求把「公式怎么变成 shader」这一步讲清楚。语法偏 HLSL/GLSL 混合。

4.1 屏幕误差 → LOD 选择

// 输入：簇的世界空间误差、簇中心到相机距离
// 目标：投影到屏幕上的像素误差
float projectedError(float objectError, float dist, float projScaleY) {
    dist = max(dist, 1e-3);
    return objectError * projScaleY / dist;   // projScaleY ≈ viewportHeight / (2*tan(fovY/2))
}

// DAG 遍历：一个线程处理一个簇，满足条件就停，否则把子簇压入队列
void traverse(uint clusterIdx, vec3 camPos, float threshold) {
    Cluster c = clusters[clusterIdx];
    float d = distance(camPos, worldCenter(c));
    if (projectedError(c.lodError, d, projScaleY) < threshold) {
        pushDraw(c);              // 这一层够用了，进光栅化列表
        return;
    }
    if (c.childCount == 0) { pushDraw(c); return; }  // 已是最精细层
    for (uint i = 0; i < c.childCount; ++i)
        queuePush(c.childStart + i);   // 否则继续向下
}
为什么用投影误差而不是距离阈值：同一个簇在 4K 屏上需要比 1080p 更精细，用距离就会在换分辨率时爆掉。阈值一般取 1.0，动态分辨率下按实际渲染分辨率缩放。

4.2 可见性缓冲写入

// 高 32 位：深度（float 位模式当作 uint 比较，正深度下单调一致）
// 低 32 位：instanceId(24bit) | triangleId(8bit)
uint64_t pack(float depth, uint instanceId, uint triId) {
    return (uint64_t(asuint(depth)) << 32) | (uint64_t(instanceId) << 8) | triId;
}
// 硬件光栅：片段着色器里 disable depth test，直接 atomicMax，无深度附件
// 软件光栅：同一套 pack + atomicMax，于是两种光栅化天然统一
imageAtomicMax(visBuffer, pixel, pack(depth, id, tri));

限制：三角形 id 只有 8 位，所以每簇必须 ≤255 个三角；instanceId 24 位够用（1600 万实例）。若簇更大就改成 16/48 位分配，或存两个通道。

4.3 屏幕探针的最终收集

// 每个像素找 4 个包围它的探针，按八面体 UV 双线性插值
vec3 finalGather(vec2 pixelUV, vec3 normal) {
    vec3 sum = 0; float wsum = 0;
    for (int i = 0; i < 4; ++i) {
        Probe p = probes[neighborProbe(pixelUV, i)];
        float w = p.baryWeight;
        w *= saturate(dot(normal, p.normal) * 0.5 + 0.5);   // 法线相似度加权，抑制背面串色
        w /= (1.0 + length(p.worldPos - pixelWorldPos));     // 距离加权，抑制远处探针污染
        sum += sampleOctahedral(p.radiance, normal) * w;
        wsum += w;
    }
    return sum / max(wsum, 1e-4);
}

4.4 时间累积与防拖影

vec3 temporal(vec3 current, vec3 history, float alpha, vec3 nCur, vec3 nHist, float dCur, float dHist) {
    // 1) 几何一致性检查：法线/深度差异大就丢弃历史
    float nDiff = 1.0 - dot(nCur, nHist);
    float dDiff = abs(dCur - dHist) / max(dCur, 1e-4);
    if (nDiff > 0.15 || dDiff > 0.05) return current;

    // 2) 邻域钳制：把历史限制在当前帧 3x3 的均值±方差内，抑制鬼影
    vec3 mu = neighborhoodMean(current), sigma = neighborhoodStd(current);
    history = clamp(history, mu - 1.5 * sigma, mu + 1.5 * sigma);

    // 3) 指数滑动平均，alpha 越小越稳但越迟钝
    return mix(history, current, alpha);   // 相机静止时 alpha 可降到 0.05
}

4.5 世界缓存查找（开放寻址版）

uint hashCell(ivec3 c) {
    return (uint(c.x) * 73856093u) ^ (uint(c.y) * 19349663u) ^ (uint(c.z) * 83492791u);
}
bool worldCacheLookup(ivec3 coord, out vec3 irradiance) {
    uint slot = hashCell(coord) & (CACHE_SIZE - 1u);
    for (uint probe = 0; probe < 8u; ++probe) {          // 线性探测，最多 8 步
        Cell cell = cells[slot];
        if (cell.life <= 0.0) return false;              // 空槽：miss
        if (all(equal(cell.coord, coord))) { irradiance = cell.irradiance; return true; }
        slot = (slot + 1u) & (CACHE_SIZE - 1u);
    }
    return false;   // 探测失败就退回环境光，避免黑色空洞
}
回收的坑：直接让 life 归零会在表里留下「墓碑」，探测链断裂导致明明存在的 cell 查不到。要么定期整体 rehash 压缩，要么用带回退的墓碑标记（值里存一个标志位，探测可穿过但不可插入）。

6.2 路线 B：UE 源码精读与改造

  1. 编译源码引擎

    Setup.bat（20~30GB 第三方库）→ GenerateProjectFiles.bat → 编译（数小时，磁盘留 150GB）。只改 shader 时可用控制台 recompileshaders changed 热验证，不必每次重编 C++。

  2. 开官方示例 + CVar 实验

    载入带 Nanite/Lumen 的示例场景，先当调参工程师：r.Nanite 0/1 对比、逐个翻 r.Lumen.* 质量档位、用 Stat GPU 观察每个 pass 的真实开销。这一步建立「量」的直觉。

  3. 按 05 章导读逐文件精读

    完成任务清单里的六条，每条都回本库核对结论。

  4. 动手改造三连（由小到大）

    ① 改 cluster 调试图或 LOD 阈值（shader 热改，当天见效）；② 加一个自定义 debug pass（如簇密度热力图）；③ 改 fallback mesh 生成参数，观察 GI 精度变化——正好验证 03 章的接口层理论。

  5. Capstone

    给 Nanite 加一个小特性并把改动过程写成博客（贴自己的 diff 与思路可以，大段引擎源码不能公开）。这是渲染岗求职最有说服力的作品。

EULA 边界：源码版 UE 自用、内部开发没问题；对外发布遵守 royalty 条款；引擎源码本身不能转发或大段公开。

6.3 路线 C：Unity SRP 落地

Unity 没有官方 Nanite/Lumen 等价物（Unity 6 的 GPU Resident Drawer + GPU Occlusion Culling 只解决实例级 GPU-driven 剔除，GI 仍是 APV 烘焙探针），所以「Unity 版虚拟几何 + 动态 GI」是真正的自研空间——而且能直接长在你日常的 Unity 工作流上。

需求Unity 里的对应物

indirect 绘制CommandBuffer.DrawProceduralIndirect / RenderMeshIndirect

完整版在独立手册里：Unity 路线内容多（SRP 前置、U0~U7 阶段、Unity 特有坑、资源清单），已单独成册 → 打开 Unity 学习手册。本页只放映射总览。

6.4 推荐组合

三条路线不用二选一，推荐这个节奏：主线走自制 A（P0~P4 打通基础管线）→ 平行开路线 B 按任务清单精读 UE 源码（每周 1~2 条）→ P5 之后用路线 C 把成熟设计搬进 Unity SRP，最终在你的实际项目里落地。A 给你原理，B 给你工程判断，C 给你产出。

6.5 从头搭，还是直接用 Carrot / Bevy？

这是路线 A 的一个变体问题：「魔改现成开源引擎当宿主」算不算第四条路线。直接给判断：

选项优势代价适合谁
完全从头搭 无黑盒，每一层都是自己写的；调试能力被逼到极致 慢；前期大量时间花在和 Nanite 无关的基建（窗口、RHI、资源加载）上 目标是「彻底搞懂原理」的人
魔改 Carrot 与本题贴合度最高：Nanite+光追接缝已打通，单人项目规模可通读，MIT 协议 孤岛项目：文档少、社区小、没有配套教程，很多设计要靠自己读代码反推 C++ 熟练、想直接研究接缝层实现的人
魔改 Bevy 活跃生态 + JMS55 的博客持续更新；meshlet 与 solari 代码质量高、可对照 ① wgpu 抽象层挡在底层 API 之上，「手撸底层」的体验打折；② meshlet 与 solari 没有打通；③ Rust 学习成本 接受 wgpu 抽象、想尽快跑起来的人
我的建议：别在「完全从头」和「直接用现成」之间二选一——它们不是竞争关系，是题目和答案册的关系。正确用法：自己从头搭主线（哪怕只到 P4），卡住时去 Carrot / Bevy 的源码里翻「这一步别人是怎么写的」。反过来，如果你选魔改 Bevy，「把 solari 接上 meshlet」本身就是绝佳的毕业课题——那正是本库 03 章讲的接口层，官方至今没做。
一个容易被低估的点：从头搭的前 30% 时间会花在和 Nanite 毫无关系的基建上（RHI 封装、资源加载、shader 编译管线）。如果这让你烦躁，那就更该走「mini 自研 + 开源当答案册」的混合路线，而不是硬扛全从头，也不是直接住进别人的引擎里。

踩坑清单

Nanite 侧

现象原因处理
LOD 切换处出现裂缝简化时没锁边界顶点，或父层簇的边界顶点与子层不是同一批简化阶段显式传 locked vertex 集合；父层重切簇时保留边界顶点索引

材质解析比光栅化还贵对全屏像素都跑了完整材质深度预通道 + 只对可见像素跑；复杂材质拆成多 pass

接口层

现象原因处理
光追画面比光栅化「少一块」簇列表只取了可见簇，屏幕外的遮挡体没进 TLAS光追用的簇集合要单独维护，包含视锥外但对 GI 有贡献的物体（比如身后那面墙）

工程组织建议：只维护两个程序——① nanite-tools：命令行工具，子命令 cluster / simplify / dag / stat，离线产出自定义资产格式 .nmesh（簇数组 + DAG + fallback）；② viewer：运行时程序，P0 先画普通模型，之后每一步都在它上面加一个可开关的模式（--mode cull / dag / hiz / visbuf / shadow / probe / cache），旧模式永远保留当对照。资产格式第一次就定好带版本号，后面加字段不破坏旧文件。 着色器语言配套选 Slang：一份 shader 编译到 SPIR-V / DXIL / Metal LIB，天然跨后端——Carrot 本身就用 slang（你本地 Carrot/engine/resources/shaders/ 里全是 .slang），语法对 HLSL 用户几乎零成本；框架 A/B 下都能用（Diligent 原生支持 Slang，wgpu 侧用 slangc 编到 WGSL/SPIR-V）。注意 WGSL 没有 64 位标量原子，wgpu 路线下 vis buffer 打包要改成两次 32 位 CAS——这条坑 Unity 手册踩坑章 同源。

NANITE · 虚拟几何

Cluster簇约 128 个三角形的分组，是切分、剔除、LOD、绘制共用的基本单位——整套管线的灵魂概念。→ 01
Meshlet网格碎片cluster 在 meshoptimizer / Bevy 里的叫法，本质完全相同；读这两家代码时别被名词绕晕。→ 06
Cluster Group簇组用 METIS 等图分割算法把空间相邻的 cluster 聚成组，组内做简化才能控制边界数量。→ 01
QEM二次误差度量Quadric Error Metric：用顶点邻域平面构成的二次型衡量「折叠这条边的变形代价」，网格简化的标准代价函数。→ 04
Boundary Lock边界锁定组内简化时禁止折叠组边界顶点，否则相邻簇之间会出现肉眼可见的裂缝——切簇方案最常见的翻车点。→ 08
Cluster DAG簇有向无环图低级簇指向简化出的父簇，每个节点记录自己的误差；不是树，因为合并可以共享父节点。→ 01
Screen-space Error屏幕误差把簇的世界空间误差按距离投影成屏幕像素数，与阈值（Nanite 默认约 1px）比较来决定 LOD。→ 04
Cut截断DAG 遍历时「误差超标就停止下钻」留下的节点集合，就是当前帧实际绘制的簇列表。→ 01
Fallback Mesh兜底网格DAG 底层的粗模副本，专供光追 BLAS、小尺寸阴影、碰撞检测使用，避免拿整套 DAG 喂光追。→ 03
Visibility Buffer可见性缓冲只存 cluster id + 三角 id（打包进 64 位），延迟到材质 pass 才展开成完整 GBuffer，是支撑海量小三角形的关键设计。→ 01
Material Pass材质解析读可见性缓冲，反查顶点数据插值出真正的材质、法线、深度——vis buffer 管线的第二遍。→ 01
Soft Raster软光栅用 compute shader 光栅化小于一个像素的三角形，绕开硬件光栅 2×2 quad 的浪费；要求像素级原子操作 + 先可见性后属性两遍走。→ 01
Hi-Z深度金字塔mipmap 化的屏幕最小深度图，保守判断簇包围盒是否被遮挡；做两遍光栅时第二遍只在可见簇上跑。→ 04
Indirect Draw间接绘制绘制参数由 compute shader 生成写进 GPU buffer，CPU 一帧只调一次 ExecuteIndirect——GPU-driven 的基石。→ 01

LUMEN · 动态全局光

GBuffer几何缓冲全屏存位置、法线、材质参数的延迟渲染中间产物；Lumen 所有光追射线都从它的像素出发。→ 02
Irradiance辐照度某点单位面积接收到的总光能量（对入射半球积分）；探针和世界缓存里存的就是它——别和 radiance 混。→ 02
Radiance辐射亮度沿单一方向的光亮度，每条光追射线返回的量；irradiance = radiance 对半球的积分。这两个词是 GI 资料的第一道坎。→ 02
Screen Probe屏幕探针屏幕空间按 4 级 cascade 布点的探针（分辨率逐级减半、间距加倍），每帧从上一帧位置重投影，缓存周围 irradiance。→ 02
Octahedral Map八面体映射把球面方向摊平成 2D 图的方式；探针用 16×16 像素存 256 个方向的 irradiance 全靠它。→ 04
Surface Cache表面缓存世界空间的持久缓存，每个 cell 存 irradiance；每帧对光源追 1 条射线 + 查邻居 cell，多弹射自然涌现——Lumen 的「世界记忆」。→ 02
Hash Grid哈希网格世界缓存的容器：位置哈希到 cell，GPU 上用 hashmap 管理分配与回收（回收时机是经典坑）。→ 04
Final Gather最终收集逐像素找到周围 4 个探针，从它们的八面体图插值采样 irradiance 并按 BRDF 加权，得到间接光。→ 02
Reprojection重投影用上一帧深度 + 运动向量找本帧对应位置，让缓存跨帧复用；移动物体和新生成的像素会失效，靠滤波兜底。→ 04
Spatiotemporal Filter时空滤波空间模糊 + 时间累积的联合降噪；GI 画面最终能不能看，八成取决于这个 pass 的调校。→ 02
Multi-bounce多弹射光经过两次以上反射形成的间接光；世界缓存天然产生，屏幕探针本身只有一跳。→ 02
BRDF双向反射分布函数描述「这个表面把入射光往某方向反射多少」的函数，PBR 着色与 final gather 加权共用的数学核心。→ 02
Ray Query光线查询VK_KHR_ray_query / DXR Inline Ray Tracing：在任意 shader 里发起求交查询。做 GI 不需要完整 RT pipeline，用它就够。→ 02
BLAS / TLAS加速结构Bottom-Level = 单个 mesh 的 BVH（可预建），Top-Level = 实例列表（每帧重建）；光追场景的两种积木。→ 03
ReSTIR GI重采样复用 GIReservoir-based Spatiotemporal Importance Resampling：从时空邻居「借」高质量光线样本，大幅降噪；Bevy solari 0.20 走的路线。→ 06
DDGI探针网格 GIDynamic Diffuse Global Illumination：世界空间规则网格放探针，比 screen probe 简单但大场景分辨率吃亏；自研 GI 的经典兜底方案。→ 02
Denoiser降噪器把低样本数蒙特卡洛噪声滤掉的后期 pass；DLSS-RR 是这一层的终极形态。→ 02

通用与接口

GPU-drivenGPU 驱动管线剔除、LOD、绘制决策全在 GPU 上完成，CPU 不做逐对象逻辑；Nanite 和 Lumen 共同的前提。→ 01
Readback回读GPU → CPU 拷数据；逐簇 BLAS 聚合需要回读簇列表，同步代价大，标准解法是延迟一帧使用。→ 03
Distance Field距离场Lumen 软光追路径的几何表示（每个网格存有符号距离场纹理）；本库建议砍掉软光追路径，知道概念即可。→ 02
Mesh Card网格卡片Lumen 软光追路径里贴到网格表面的矩形捕获卡，表面缓存的载体——同属「被砍路线」，工程量比 Nanite 本体还大。→ 02
Cascade级联近细分远粗略的多级结构；探针布局和距离场都用它平衡近处精度与远处覆盖。→ 02
Vis Buffer 的 64 位打包打包约定高 32 位放 cluster id、低 26 位放三角 id 的典型布局；写光栅 shader 前先定死，改一次全家重编译。→ 04
